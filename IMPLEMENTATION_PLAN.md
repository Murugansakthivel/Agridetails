# Agridetails.com — Implementation Plan

_Companion to `PROJECT_AUDIT.md`. This is a **future-state plan**, not a
build log — nothing described below as "target"/"future" exists in the repo
yet unless explicitly marked otherwise. Where this plan references a
"master spec," it means the broader Agridetails platform spec that this
repo's current prototype is the first slice of; section numbers (§38, §47,
§60) are as cited in the working brief for this document._

Key properties: **no backend, no database, no auth, no build step.** Every
"data source" is a committed JavaScript file. Internationalization is
client-side dictionary lookup. Deployment is push-to-deploy via GitHub
Pages Actions with zero gating (no tests, no lint).

## 2. Target architecture (master spec)

The master spec describes a considerably larger platform than what's built.
Target shape:

```

│ Frontend (optional rewrite) │   Angular or React + TypeScript
│ — replaces static HTML/JS   │   (current static site can also just grow
└──────────────┬───────────────┘   an API client layer instead of a full
               │ HTTPS/JSON          rewrite — see §5 migration note)
               ▼
┌─────────────────────────────────────────────────────────┐
│              .NET 8 Web API backend                      │
│  Controllers/minimal APIs · auth (JWT/OAuth) · validation │
│  ┌─────────────────────────────────────────────────────┐ │
│  │ AI provider abstraction layer:                       │ │
│  │   IAgricultureVisionProvider  (Crop Doctor photo→dx)  │ │
│  │   IAgricultureTextProvider    (symptom text → dx/Q&A) │ │
│  │   — concrete impls swap in behind these interfaces    │ │
│  └─────────────────────────────────────────────────────┘ │
│  Background workers (scrapers/cron → DB, replacing the    │
│  current "write a JS file and commit" pattern)             │
└───────┬───────────────┬───────────────┬───────────────────┘
        │                │                │
        ▼                ▼                ▼
  PostgreSQL         Redis cache      S3-equivalent storage
  (~30 tables,        (session,       (user-uploaded crop
   see §4)            price/weather   photos, scraped raw
                       cache)          docs, report exports)
```

Deployment target: GitHub Pages (now) → AWS (S3+CloudFront for static
frontend, ECS for the API, RDS for Postgres, ElastiCache for Redis) — see
§9.

**This is a large jump from the current repo.** The rest of this plan is
organized to get there incrementally without breaking what already works.

## 3. Prototype Mode acknowledgment (master spec §47)

The master spec's own **§47 "Prototype Mode"** explicitly allows building
working prototypes with mock/demo data, provided that data is **clearly
labeled** and **never presented as live production data**. The current
repo already follows this discipline in practice, even before this plan
existed:

- `js/agri-stocks.js` header: "**NOT** a live feed... periodically-
  refreshed snapshot."
- `js/prices-data.js` / `js/crops-catalog.js`: labeled demo/estimated
  pending real sourcing.
- `js/fertilizer-shops.js`: explicitly labeled **real** scraped data (not
  mock), with unavailable fields (address, pesticide stock) left blank
  rather than invented.
- The forthcoming `crop-doctor.html` (built concurrently — see §6) is
  planned as a rule-based **mock** knowledge base for 5 crops
  (tomato/chili/paddy/banana/cotton), explicitly labeled DEMO/prototype AI,
  not a real vision model.

**Roadmap implication:** every new feature in the backlog below should
continue this pattern — ship as a labeled prototype/mock first where a real
backend/AI/data source isn't ready yet, rather than blocking on full
backend build-out or silently faking realism. The label must be visible to
the end user (banner/badge in the UI, not just a code comment), matching
what `initPrices()` already does with its live/demo source banner
(`t('live_banner')` vs `t('demo_banner')`).

## 4. Database plan (future state — not built now)

Sketch of the ~30-table schema the master spec calls for. Grouped by
domain; exact columns to be finalized at implementation time.

**Identity & farms**
`users`, `roles`, `user_roles`, `farms`, `farm_members`, `crops` (crop
taxonomy, distinct from `farm_crops`), `farm_crops`

**Crop Doctor / AI**
`crop_doctor_cases` (one row per diagnosis request: farm/user, crop, photo
ref, symptom text, timestamp), `ai_diagnoses` (result of a case: provider
used, confidence, disease id, recommended treatment, raw provider
response), `pest_disease_catalog` (successor to today's
`js/advisory-kb.js`, normalized into the DB)

**Market / environment data**
`market_prices` (successor to `crops-catalog.js`/`prices-data.js`),
`markets` (mandi reference table), `weather_observations`, `climate_alerts`
(successor to `climate-news.js`'s `history[]`), `dams` (successor to
`dam-details.js`), `dam_readings` (time series, since dam levels are
already per-reading `dateAsOf` in the current data)

**News & schemes**
`news` (successor to the hardcoded `NEWS_ITEMS` array in `app.js`),
`government_schemes`, `scheme_eligibility_rules`

**Farm operations**
`farm_tasks` (smart calendar), `farm_task_templates`, `notifications`,
`notification_preferences`

**Commerce / directory**
`shops` (successor to `fertilizer-shops.js` + its overrides file —
`shop_overrides` collapses naturally into nullable columns on `shops` once
there's a real DB instead of a two-file merge pattern), `shop_products`,
`shop_stock_readings` (time series, since stock is refreshed daily),
`partners`, `partner_categories`

**Stocks watchlist**
`stock_symbols`, `stock_price_snapshots` (successor to `agri-stocks.js`),
`stock_news`

**Platform / ops**
`audit_logs`, `admin_users`, `feature_flags`, `scrape_jobs` (job run
history — successor to the informal `scripts/.cache/*.json` resumable-cache
pattern), `api_keys` (for any future partner/B2B API access)

This is a **planning sketch**, not a migration script — actual DDL should
be written per-sprint as each domain is implemented (see §8), starting with
whichever table group unblocks the first P0/P1 backlog item.

## 5. API plan (REST, master spec §38 sketch)

Representative endpoints per domain (not exhaustive — filled in per sprint):

```
POST   /api/v1/auth/register            /login          /refresh
GET    /api/v1/users/me
GET    /api/v1/farms                    POST /api/v1/farms
GET    /api/v1/farms/{id}/crops         POST /api/v1/farms/{id}/crops

POST   /api/v1/crop-doctor/cases        (upload photo + symptoms)
GET    /api/v1/crop-doctor/cases/{id}   (poll for AI diagnosis result)
GET    /api/v1/crop-doctor/kb           (disease catalog, public read)

GET    /api/v1/market-prices?crop=&market=&date=
GET    /api/v1/weather?lat=&lon=        /climate-alerts?district=
GET    /api/v1/dams?district=
GET    /api/v1/fertilizer-shops?district=&search=
GET    /api/v1/stocks?group=            /stocks/{symbol}
GET    /api/v1/news?tag=
GET    /api/v1/government-schemes?crop=&state=

GET    /api/v1/farms/{id}/tasks         POST /api/v1/farms/{id}/tasks
GET    /api/v1/notifications            POST /api/v1/notifications/mark-read

-- Admin (role-gated) --
POST   /api/v1/admin/shops/{id}/override
POST   /api/v1/admin/news
GET    /api/v1/admin/audit-logs
```

Design notes carried over from the current static site's good habits:
- Keep a `source`/`asOf` field on every read response (the current site
  already does this per-dataset — `AGRI_STOCKS.asOf`, `DAM_DETAILS.asOf`,
  each price row's `updated`) so the frontend can keep showing "data as of"
  banners with zero special-casing.
- Every list endpoint should support the same filter shape the current
  client-side `filtered()` functions already use (district, search term,
  category) so the frontend filter UI (§6 below) ports over almost
  unchanged, just swapping a local array filter for a query-string request.

## 6. AI architecture plan

**Abstraction (target, .NET backend):**
```csharp
public interface IAgricultureVisionProvider {
    Task<VisionDiagnosisResult> DiagnoseAsync(Stream photo, string cropHint, CancellationToken ct);
}
public interface IAgricultureTextProvider {
    Task<TextDiagnosisResult> DiagnoseAsync(string symptomText, string cropHint, CancellationToken ct);
}
```
Concrete implementations (e.g. a hosted vision model, a third-party
agriculture AI API, or a fine-tuned model behind an internal endpoint) are
swapped in behind these two interfaces without the frontend ever knowing
which provider answered. A `MockAgricultureProvider` implementing both
interfaces from the same rule-based logic the prototype already uses is the
natural **first** implementation — it lets the backend, DB, and API contract
all get built and tested before any real AI vendor integration is
committed to.

**How the current/concurrent prototype maps onto this:**

| Today (prototype) | Future (backend) |
|---|---|
| `advisory.html` + `js/advisory-kb.js`: keyword-matches free-text symptoms against 8 static disease entries, EN/TA. Photo is displayed but **not analyzed** — see `PROJECT_AUDIT.md` §5. | `IAgricultureTextProvider` — same keyword-match logic can literally become the `MockAgricultureTextProvider` implementation server-side. |
| `crop-doctor.html` (being built concurrently, separate agent): rule-based mock KB for tomato/chili/paddy/banana/cotton, explicitly labeled DEMO/prototype AI, client-side only. | `IAgricultureVisionProvider` mock: same rule logic moves server-side behind `POST /api/v1/crop-doctor/cases`; frontend swaps a local JS lookup for an HTTP call but the **UI/UX contract stays the same** (upload photo, enter symptoms, get name + pesticide + dose + wait period back). |
| No image analysis at all. | Real `IAgricultureVisionProvider` implementation calls an actual vision model/API; response shape stays identical to the mock's (`VisionDiagnosisResult`), so the frontend requires **no changes** when the swap happens — only the DEMO badge is removed and a confidence/"AI-generated, verify with KVK" disclaimer stays. |

**Key design commitment:** the frontend must talk to `/api/v1/crop-doctor/*`
in a shape that doesn't change between mock and real providers. This is
what makes the current prototype (client-side rule engine) a legitimate,
non-throwaway first step rather than a dead end — the *data shape* it
already returns (`{name, symptoms, pesticides:[{name,dose,wait}],
prevention}`, per `js/advisory-kb.js`) should be treated as the working
draft of `VisionDiagnosisResult`/`TextDiagnosisResult` when the real schema
is written.

## 7. Admin architecture plan (future)

Not built. Planned shape: a role-gated admin area (could be a separate
`/admin` frontend route behind auth, or a lightweight separate admin SPA)
covering:
- Dataset overrides UI replacing hand-editing
  `fertilizer-shops-overrides.js` (and its future siblings for other

- Scrape job monitor (status/last-run/errors for the 3 daily jobs +

- Audit log viewer (`audit_logs` table, §4).

## 8. Deployment architecture plan

**Now:** GitHub Pages, static files only, deployed via
`.github/workflows/deploy.yml` on every push to `main`. No environments, no
staging slot, no rollback mechanism beyond `git revert`.

**Future (per master spec):**
- Frontend: S3 + CloudFront (or keep GitHub Pages for the public marketing
  site and move only the authenticated app portion to S3/CloudFront —
  decide per actual traffic/cost needs, not assumed up front).
- API: ECS (containerized .NET 8 API), behind an ALB.
- Database: RDS (PostgreSQL).
- Cache: ElastiCache (Redis).
- Object storage: S3 (crop photos, exports).
- CI/CD: extend the existing GitHub Actions setup with build/test gates
  before the deploy step (currently missing — see `PROJECT_AUDIT.md` §7)
  rather than replacing it outright.

## 9. Sprint plan (2-week sprints, master spec §60 Phase 1–9 alignment)

| Sprint | Phase (§60) | Focus |
|---|---|---|
| 1–2 | Phase 1 — Foundation | Stand up .NET 8 API skeleton + Postgres locally; port 3–4 highest-value read-only datasets (market prices, dams) into the DB behind the API; keep the static frontend, point one page at the new API as a pilot. |
| 3–4 | Phase 2 — Core data services | Finish migrating remaining datasets (fertilizer shops, stocks, climate/news) into DB-backed endpoints; move the 3 daily scrapers from "write JS + commit" to "write DB via background worker." |
| 5–6 | Phase 3 — Auth & farm profiles | Users/roles/farms tables; login; farm profile CRUD; still no AI. |
| 7–8 | Phase 4 — Crop Doctor backend (mock provider) | `IAgricultureVisionProvider`/`IAgricultureTextProvider` interfaces + `MockAgricultureProvider`; `crop_doctor_cases`/`ai_diagnoses` tables; wire the (by-then-existing) `crop-doctor.html` prototype to call the real API instead of its local rule engine, still clearly labeled DEMO. |
| 9–10 | Phase 5 — Real AI vision integration | Swap in a real vision provider behind the same interface; add confidence scoring, human-verification disclaimer, KVK contact callout (already exists as a pattern from commit `7768ed5`'s KCC helpline work). |
| 11–12 | Phase 6 — Notifications & weather | `weather_observations` live integration, `notifications` table, push notification delivery. |
| 13–14 | Phase 7 — Government schemes & smart calendar | `government_schemes` + `farm_tasks` modules. |
| 15–16 | Phase 8 — Admin dashboard | Admin auth, dataset override UI, scrape job monitor, audit log viewer. |
| 17+ | Phase 9 — Partners/marketplace/B2B | Only after everything above is stable — see backlog P3. |

Each sprint should ship independently deployable, working software — no
"big bang" cutover. The static site keeps working throughout; pages migrate
to the API one at a time.
